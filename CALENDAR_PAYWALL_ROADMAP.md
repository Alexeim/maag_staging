# Роадмап: защита календаря (регистрация сейчас, подписка в сентябре)

## Проблема

Сейчас "гейт" на `/calendar` — это чисто визуальный трюк: вся секция с событиями
оборачивается в CSS `blur-sm` на основе клиентского Alpine-стора
(`$store.auth`), см. [src/pages/calendar.astro:284](src/pages/calendar.astro#L284).

При этом **все данные событий уже лежат в HTML** — они зашиваются в
`calendarState` через `JSON.stringify` на сервере при рендере страницы
([calendar.astro:207-223](src/pages/calendar.astro#L207-L223)) независимо от
того, залогинен посетитель или нет. Источник данных —
`GET /api/public/calendar` →
`buildCalendarPagePayload()` в
[server/src/controllers/publicLandingController.ts:786](server/src/controllers/publicLandingController.ts#L786) —
тоже отдаёт полные данные всем, без проверки авторизации.

Это значит: снять блюр через devtools, посмотреть "View Page Source" или
просто `curl` эндпоинт — три равноценных способа увидеть всё (адрес, билеты,
описание, название, дату) в обход "защиты".

## Главный принцип

**Решение о том, что отправить, принимает сервер, на основе проверенного
статуса — до того как ответ ушёл клиенту.** Блюр/CSS — это только полировка
поверх уже урезанных данных, никогда не сама граница защиты (потому что блюр
всегда снимаем в devtools, для любого сайта, в любой реализации).

## Ключевые решения, принятые в обсуждении

1. **Секрет — вообще всё**, не только адрес/билеты. Название события и дата
   тоже не должны быть видны/угадываемы неавторизованным пользователем.
2. **Дизайн не меняется.** Блюр уже делает текст нечитаемым, поэтому
   "настоящее название под блюром" и "заглушка под блюром" визуально
   неотличимы. Значит фронтенд/CSS/типографику трогать не нужно — меняются
   только данные, которые в неё подставляются.
3. **Никаких skeleton-плашек/лоадеров** — ломает ощущение премиального
   редакционного дизайна сайта.
4. **Заглушка — не lorem ipsum, а осмысленный текст**: на месте названия —
   что-то вроде `"Событие для подписчиков"`, на месте даты — `"Открыть
   доступ →"`. Если кто-то всё же снимет блюр — увидит осознанное сообщение,
   а не "битые тестовые данные".
5. **Картинка блюрится по-настоящему на сервере** (пиксельно, через `sharp` —
   уже есть в зависимостях бэка и используется как прецедент в
   [server/scripts/compressStorageImages.js](server/scripts/compressStorageImages.js)),
   а не CSS-трюком — иначе оригинал всё равно можно достать из DOM.
6. **SEO нельзя терять.** Гуглобот — тоже "неавторизованный" запрос с точки
   зрения сервера, значит по умолчанию он тоже получил бы заглушки, и Google
   перестал бы индексировать реальные события. Решение — официальный
   гугловский паттерн **Flexible Sampling** (используют NYT/WSJ/Bloomberg для
   пэйволов): верифицированному гуглоботу отдаём полные данные, всем
   остальным — заглушки.
7. **Сейчас — только регистрация, подписка в сентябре.** Граница защиты сразу
   ставится на уровне authenticated-эндпоинта, поэтому добавление проверки
   подписки в сентябре — это всего одна дополнительная проверка на том же
   эндпоинте, без переделки архитектуры.

## Как это будет выглядеть для неавторизованного пользователя

Визуально — **один в один как сейчас**:

1. Заходит на `/calendar` — заголовок, карусель "Главных событий" крутится,
   листается стрелками, всё как сегодня.
2. Каждая карточка — реально заблюренное фото + текст на месте
   названия/даты (те же шрифты/позиции/размеры), тоже заблюренный.
3. Модалка по центру "MAAG — Только для подписчиков" с кнопками
   "Войти"/"Оформить подписку" — без изменений.
4. Логинится → модалка закрывается, блюр снимается, на карточках проступают
   настоящие название/дата/адрес/фото — без перезагрузки страницы.
5. Не логинится → так и остаётся с блюром и заглушками навсегда. Снятие
   блюра через devtools ничего не даёт — под ним физически нет реальных
   данных.

## Технический план

### Бэк

1. **Утилита верификации гуглобота** — `isVerifiedGooglebot(ip, userAgent)`:
   обратный DNS-лукап IP → должен резолвиться в `*.googlebot.com`/`*.google.com`
   → затем **обратная проверка** (forward DNS на полученный хостнейм должен
   вернуть тот же IP). Просто проверка `User-Agent` не годится — подделывается
   одной строкой.
2. **`GET /api/public/calendar`** — один эндпоинт, логика в три ветки:
   - Валидный Bearer-токен (юзер залогинен) → полные данные.
   - Верифицированный гуглобот → полные данные (для индексации).
   - Все остальные → заглушка (текст-плейсхолдер + путь до
     сервер-заблюренной картинки).
3. **Structured data**: в
   [src/lib/seo/structuredData.ts](src/lib/seo/structuredData.ts)
   у `buildEventStructuredData` добавить `isAccessibleForFree: false` — честно
   сообщает Google, что контент платный, без пессимизации в выдаче.

### Фронт

4. **`calendar.astro`** должен прокинуть **настоящий IP/User-Agent
   посетителя** в запрос к бэку. Важный нюанс: сама Astro-страница рендерится
   на вашем сервере и делает server-to-server запрос к `server/` API — бэк по
   умолчанию увидит IP/UA **Astro-сервера**, а не оригинального визитёра.
   Нужно явно прокинуть `Astro.clientAddress` и
   `Astro.request.headers.get('user-agent')` как доп. заголовки в fetch к
   бэку, иначе верификация гуглобота на шаге 2 не будет работать.
5. **Клиент**: после логина `$store.auth.isLoggedIn === true` → тот же
   эндпоинт, но уже запрос из браузера с Bearer-токеном → бэк отдаёт полные
   данные → подставляются в карточки, блюр снимается.

### Сентябрь (не сейчас)

6. На эндпоинт из шага 2 добавляется ещё одна проверка — активная подписка
   (`stripeSubscriptionStatus === 'active' | 'trialing'`, уже пишется в
   Firestore из [server/src/controllers/stripeController.ts](server/src/controllers/stripeController.ts),
   просто пока никто это не читает как условие доступа). На клиенте условие
   меняется с `isLoggedIn` на `isLoggedIn && isSubscribed`. Всё остальное — не
   трогается.
